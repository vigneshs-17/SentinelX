# Operations

How to run, watch and fix SentinelX. Every command here exists in this repository; nothing is described that was not run.

## Processes and files

| Process | Command | Needs | Writes |
| --- | --- | --- | --- |
| Sensor | `python main.py sensor` | capture privilege (root, or `CAP_NET_RAW`; Npcap on Windows). Live capture in a container is not tested in CI | `alerts.db`, `alerts.jsonl`, heartbeat rows |
| API + console | `python main.py api` | nothing special; opens `alerts.db` read-only | `app.db` (users, sessions, keys, triage, audit) |
| PCAP replay | `python main.py replay file.pcap` | nothing special | same as the sensor |
| Development | `python main.py run --dev` | capture privilege | both, in one process; Flask dev server, never expose |

`main.py api` refuses to start if `alerts.db` does not exist (start the sensor first) or if no admin user exists. Create the first admin with
`python main.py user add <name> --role admin` (the password is prompted, never an argument).

### First run, Linux (Docker)

```bash
docker compose run --rm api python main.py user add admin --role admin
docker compose up -d
```

The console is on `http://127.0.0.1:5000/`. Docker Desktop on Windows or macOS cannot capture the host network card; there, run the sensor natively
(Windows: install Npcap, then `python main.py sensor`) and the API natively or in Docker.

### Behind a reverse proxy / HTTPS

Terminate TLS at the proxy, set `SENTINELX_HTTPS=true` (Secure cookie, HSTS) and list the proxy's address in `SENTINELX_TRUSTED_PROXIES` so the
login lockout and rate limits see the real client address. The API never trusts `X-Forwarded-For` from anyone else.

### Backups

`alerts.db` and `app.db` are SQLite files in WAL mode. Back them up with `sqlite3 <file> ".backup <copy>"` (a plain file copy of a live WAL database can be
inconsistent). `app.db` holds users and the audit log; losing it means re-creating users and API keys.

## Runbook

### The sensor is offline (banner in the console, `sensor_online: false`)

1. `curl -s -H "Authorization: Bearer <key>" http://127.0.0.1:5000/api/v1/sensor/status` shows `last_seen` and `age_seconds`.
2. Is the process up? Docker: `docker compose ps` and `docker compose logs sensor`. Native: check the terminal or service log.
3. Container health check: `docker compose exec sensor python scripts/healthcheck.py sensor` (exit 0 = a heartbeat newer than 30 s).
4. Common causes: no capture privilege (look for a permissions error in the log), wrong interface (`SENTINELX_INTERFACE`), the sensor writing a different
   `SENTINELX_DB_PATH` than the API reads, a full disk.
5. Alerts are not lost while the API is down; the sensor keeps writing `alerts.db`. Alerts are lost while the sensor is down.

### Drop rate is rising (health view warns above `SENTINELX_DROP_WARN_RATIO`)

The sensor has one bounded queue (`SENTINELX_QUEUE_SIZE`); when the engine cannot keep up, new packets are dropped and counted (`dropped` / `received`).
Dropped packets are never analysed, so a sustained drop rate means detections can be missed.

1. Compare `pps_10s` in the health view with the throughput the benchmark measured on comparable hardware (README, Results).
2. Look at `queue_depth` and `state_size` / `evictions`: constant evictions mean a detector table is at its cap (`SENTINELX_CAP_*`).
3. Reduce the traffic the sensor sees (mirror only the segment you care about) or give it a faster core: the packet path is single-threaded by design (see DESIGN.md).
4. Raising `SENTINELX_QUEUE_SIZE` only absorbs bursts; it does not raise sustained throughput.

### The database is growing

1. Retention runs in the live sensor (never in `replay`): `SENTINELX_RETENTION_DAYS` (default 30; `0` disables) and heartbeat history `SENTINELX_STATUS_RETENTION_HOURS`. It deletes by the time a row was **ingested** (wall clock), not by the packet time in the alert, so replaying an old capture cannot delete its own alerts.
2. Prune by hand: `python main.py db prune --older-than 14d` (accepts `Nd` or `Nh`; same ingest-time rule). It also deletes the triage rows of the alerts it removed; the API process does the same every 15 minutes, together with deleting expired sessions.
3. SQLite does not shrink the file when rows are deleted; the space is reused. To return it to the OS, stop the sensor and run `sqlite3 alerts.db VACUUM`.
4. The JSONL log rotates at `SENTINELX_MAX_LOG_SIZE` bytes and keeps `SENTINELX_MAX_LOG_BACKUPS` files.
5. The audit log in `app.db` is append-only in normal operation (a database trigger refuses UPDATE and DELETE). Retention is `SENTINELX_AUDIT_RETENTION_DAYS` (default 365; `0` keeps it forever) and is applied only when an administrator runs `python main.py db prune-audit` on the host; the prune is itself recorded in the audit log. Back up `app.db` first if you need the old rows.

### Rotating an API key (scripts, SIEM) or a password

- Keys: `python main.py apikey create --role analyst --name siem-2027` (printed once), switch the consumer, then `python main.py apikey list` and
  `python main.py apikey revoke <id>`. A revoked key stops working on its next request.
- Passwords: `python main.py user reset-password <name>` (also ends that user's sessions). `user disable <name>` ends sessions immediately.
- Suspected session theft: an admin can revoke all sessions of a user in Admin -> Users.
- The ML signing key (`SENTINELX_MODEL_KEY`) is separate: changing it means re-signing the model, see "Re-training the model".

### A webhook is failing

1. The console's Sensor health view and `/api/v1/sensor/status` show `webhook_failures` (a counter since sensor start).
2. Delivery is a background thread with 3 retries and exponential backoff; a failed alert is dropped from the webhook only. It is still in `alerts.db`.
3. The log line names the attempt and the exception class, never the URL (the URL is a secret). Typical causes: wrong URL, TLS error, the receiver rate-limiting.
4. To change the URL, set `SENTINELX_WEBHOOK_URL` and restart the sensor. To stop notifications, unset it.
5. The same (threat type, source) is sent at most once per `SENTINELX_WEBHOOK_COOLDOWN` seconds of event time; repeated alerts inside it are suppressed on purpose.

### Locked out of the console

Login lockout is per IP and per username (`SENTINELX_LOGIN_MAX_FAILURES` in `SENTINELX_LOGIN_WINDOW`, then a growing delay) and lives in API process memory.
Waiting out the shown time works; restarting the API process clears it. If the only admin forgot the password, run `python main.py user reset-password <name>` on the host.

### Re-training the model (optional; ML is off by default)

The flow model only reaches the alert path if a held-out replay shows it beats rules-only and a signed gate file says PASS. The whole procedure, with the dataset
requirements and the exact commands, is in `docs/DATASET.md`; the latest result (or "NOT RUN") is in `docs/ML_REPORT.md`.

1. Build flows from PCAPs: `python scripts/build_flows.py <pcaps> --out flows.csv.gz`.
2. `SENTINELX_MODEL_KEY=<16+ random bytes> python main.py train --flows flows.csv.gz --out models`.
3. `python main.py eval --pcap <pcaps> --labels models/test_labels.json --ml-model models --out eval_output` writes `ml_eval.json` and the signed `gate.json`.
4. Enable only with `SENTINELX_ML=on` and the same `SENTINELX_MODEL_KEY` in the sensor's environment. Any verification or gate failure disables ML and logs why.
